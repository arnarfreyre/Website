ClickHouse Tables Mastery

CREATE TABLE & INSERT Operations Guide

Understanding ClickHouse Tables

ClickHouse is a columnar database optimized for analytical queries. While it shares SQL syntax with traditional databases, it introduces powerful concepts like table engines that determine how data is stored, indexed, and queried.

Unlike traditional SQL databases, ClickHouse requires you to specify a table engine. The engine determines the table's behavior, performance characteristics, and features.

Basic CREATE TABLE Syntax

The Foundation

CREATE TABLE table_name (
    column_name1 DataType1,
    column_name2 DataType2,
    ...
) ENGINE = EngineName()
ORDER BY (column_name);

Your Example Explained

CREATE TABLE products (
    id UInt32,        -- Unsigned 32-bit integer
    name String,      -- Variable-length string
    price Float64     -- 64-bit floating point
) ENGINE = MergeTree()
ORDER BY id;
Component Purpose ClickHouse Specific?
CREATE TABLE Standard SQL table creation No
UInt32, Float64 Precise data types for optimization Yes - More specific than SQL's INT/FLOAT
ENGINE Defines storage and query behavior Yes - Unique to ClickHouse
ORDER BY Physical data sorting on disk Yes - Not just for queries, but storage

MergeTree Engine Deep Dive

MergeTree is ClickHouse's most powerful and commonly used engine family. It provides:

  • 📊 Sorted storage - Data physically sorted by ORDER BY columns
  • 🔍 Primary indexes - Automatic sparse indexing for fast queries
  • 🗜️ Data compression - Columnar storage with excellent compression
  • 🔄 Background merges - Continuously optimizes data storage
CREATE TABLE events (
    event_date Date,
    user_id UInt64,
    event_type String,
    value Float32
) ENGINE = MergeTree()
ORDER BY (event_date, user_id);

Key Point: ORDER BY with multiple columns creates a compound sorting key. Queries filtering by event_date will be very fast!

CREATE TABLE metrics (
    timestamp DateTime,
    metric_name String,
    value Float64,
    tags Array(String)
) ENGINE = MergeTree()
PARTITION BY toYYYYMM(timestamp)
ORDER BY (metric_name, timestamp);

Key Point: PARTITION BY creates separate data folders. Old partitions can be dropped instantly without scanning data!

CREATE TABLE user_actions (
    user_id UInt64,
    action_time DateTime,
    action_type Enum8('click' = 1, 'view' = 2, 'purchase' = 3),
    product_id UInt64,
    revenue Decimal64(2)
) ENGINE = MergeTree()
PARTITION BY toYYYYMM(action_time)
ORDER BY (user_id, action_time)
PRIMARY KEY user_id
SETTINGS index_granularity = 8192;

Key Points:

  • PRIMARY KEY can differ from ORDER BY (must be a prefix)
  • Enum8 saves space vs String for categorical data
  • Decimal64(2) for precise monetary values
  • index_granularity controls index density

INSERT Operations

Basic INSERT

INSERT INTO products (id, name, price)
VALUES
    (1, 'Laptop', 999.99),
    (2, 'Mouse', 29.99),
    (3, 'Keyboard', 79.99);

INSERT with SELECT

INSERT INTO products_backup
SELECT * FROM products
WHERE price > 50;

INSERT with FORMAT

INSERT INTO products FORMAT CSV
4,"Monitor",299.99
5,"SSD Drive",149.99
6,"RAM Module",89.99
ClickHouse performs best with bulk inserts (>1000 rows). Avoid single-row inserts in production. Use batching or buffering mechanisms!

Best Practices Summary

  • ✅ Choose ORDER BY wisely - It's your primary query optimization
  • ✅ Use appropriate data types - UInt64 for IDs, DateTime for timestamps
  • ✅ Batch your inserts - Aim for 10K-1M rows per INSERT
  • ✅ Consider partitioning - For time-series data, partition by month/day
  • ✅ Use PRIMARY KEY - When different from ORDER BY for optimization
  • ❌ Avoid many small inserts - They create too many parts
  • ❌ Don't over-partition - Too many partitions hurt performance
